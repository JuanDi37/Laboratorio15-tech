introduccion

Introducción

El almacenamiento convencional suele indicar dónde buscar un archivo: una ruta, un servidor y un nombre. Esa referencia puede conservarse aunque el contenido cambie. En almacenamiento por contenido, la identidad se vincula con una representación criptográfica de los bytes. Analizamos cómo esa diferencia permite verificar integridad y compartir datos sin depender de una única ubicación.

Un venture necesita decidir qué publica y quién lo conserva antes de elegir un gateway. La descentralización de la resolución no vuelve privados los datos ni crea una obligación de permanencia. Desarrollamos una política aplicada a documentos públicos, registros operativos y secretos, y presentamos un cálculo local reproducible para distinguir el identificador de un servicio de almacenamiento.

instrucciones

Instrucciones del laboratorio

En este laboratorio trabajamos en Visual Studio Code para desarrollar un informe sobre almacenamiento descentralizado utilizando un archivo venture-hello.json sin datos personales y una política de almacenamiento aplicada a un venture. Definimos una representación exacta en UTF-8, calculamos su SHA-256 y construimos un CIDv1 con codec raw para un único bloque pequeño, dejando explícito que este cálculo local no equivale a una publicación en IPFS. Explicamos el procedimiento de incorporación del archivo con IPFS, la relación entre bloques, multihash y direccionamiento por contenido, y la necesidad de mantener parámetros consistentes para obtener identificadores reproducibles. Describimos cómo Pinata conserva una copia mediante pinning y cómo un gateway HTTP recupera contenido identificado por CID, diferenciando respuestas ilustrativas de una consulta realmente ejecutada. Implementamos una experiencia interactiva que recorre archivo, CID, Pinata y gateway, compara dos variantes predefinidas del JSON y verifica los bytes del archivo local recuperado. Elaboramos STORAGE.md con categorías de sensibilidad, responsables, durabilidad, revisión y eliminación, distinguiendo materiales apropiados para publicación pública de información que requiere almacenamiento convencional. Analizamos disponibilidad, persistencia, dependencia del proveedor y los límites de retirar copias distribuidas. Entregamos el HTML, CSS, JavaScript, JSON y README correspondientes, con diagramas, matriz de clasificación, resultados calculados en el navegador y conclusiones sobre integridad y gobierno de datos.

objetivos

Objetivos

Identidad reproducible

Relacionamos bytes, codificación, hash, codec y CID. Comparamos una modificación mínima con el objeto original para observar cómo cambia la identidad.

Disponibilidad operativa

Distinguimos un identificador válido de un archivo servido. Analizamos copias, pinning, financiación y dependencia de gateways.

Gobierno de publicación

Clasificamos contenidos según sensibilidad y durabilidad. Elegimos almacenamiento de acuerdo con el derecho a retirar datos y la finalidad del venture.

tecnologias

Tecnologías utilizadas

IPFS

Organiza y transfiere bloques identificados por contenido. El CID describe una representación y permite verificar el bloque que se recibe; no indica un servidor fijo.

Pinata

Actúa como servicio gestionado para mantener archivos disponibles. El estado de pinning pertenece al servicio y debe observarse independientemente de tener un CID.

Gateway HTTP

Permite acceder desde un navegador convencional. Traduce una solicitud por contenido a una respuesta web y participa en el rendimiento, disponibilidad y observabilidad del acceso.

Web Crypto

Utilizamos SHA-256 del navegador para cálculos locales. TextEncoder convierte las cadenas a UTF-8 y un codificador base32 expresa los bytes del CIDv1.

desarrollo

Desarrollo del laboratorio

01 / Fijar el objeto y sus bytes

El archivo de ejemplo contiene únicamente un saludo, el nombre ficticio de un venture y una versión. No incluye personas, contactos, documentos de identidad ni identificadores de clientes. La representación elegida es compacta, UTF-8 sin BOM y sin salto de línea final. Esos detalles forman parte del experimento porque el hash opera sobre bytes y no sobre una interpretación visual del JSON.

Dos documentos con las mismas propiedades pueden producir hashes diferentes si cambia el orden de las claves, la sangría o un salto de línea. La igualdad semántica de JSON no asegura igualdad binaria. Para nuestros resultados comparamos los bytes exactos del archivo incluido con una cadena canónica declarada en el código, evitando depender de cómo un editor reformatea la vista.

02 / Construir y entender el CID

La representación usada en esta demostración es un único bloque raw pequeño. Construimos CIDv1 con los bytes 0x01 para versión, 0x55 para codec raw y el multihash 0x12 0x20 para SHA-256 de treinta y dos bytes. La forma textual agrega el prefijo b de base32. Es un CID calculado realmente sobre el fixture local; no afirmamos que otros nodos posean ese bloque.

Para un archivo grande o una raíz UnixFS, el multihash suele describir el bloque raíz del DAG, no el hash directo de todo el archivo. El codec, la división en bloques y el formato importan. Mantener contenido y parámetros de importación es parte de la reproducibilidad. Esta distinción está documentada en IPFS: identificadores de contenido.

03 / Incorporar, conservar y resolver

En un nodo IPFS local, el procedimiento de referencia incorpora el archivo pequeño con parámetros explícitos. Si conserva los mismos bytes y produce una única hoja raw como raíz, el CID coincide con el cálculo de esta página. No ejecutamos estos comandos en una red IPFS en esta entrega: mostramos el procedimiento completo y explicamos cómo leer su salida.

El pin local protege de la recolección de basura de ese nodo. Un servicio remoto agrega otra responsabilidad de conservación. En Pinata se selecciona almacenamiento público IPFS, se carga el mismo archivo y se comprueba el CID y el estado de disponibilidad informado por el servicio. Un identificador de carga, la aceptación de una solicitud y una recuperación correcta son estados distintos. Ningún token de API forma parte de los archivos de esta web.

La solicitud de gateway utiliza la ruta /ipfs/CID o un subdominio equivalente. Un HTTP 200 indicaría una respuesta exitosa, pero no demuestra por sí solo que los bytes sean correctos. Un error puede reflejar demora de descubrimiento, ausencia de proveedores, límites del gateway o contenido no disponible. Verificar el digest permite separar integridad del funcionamiento del transporte.

04 / Aplicar STORAGE.md

Nuestro venture ficticio publica manuales y demostraciones que toleran replicación pública. Conserva contratos de clientes y registros internos en almacenamiento con control de acceso, vencimientos y auditoría. Excluye secretos y datos personales de cualquier publicación permanente. La clasificación es una decisión previa: cifrar un documento no garantiza borrado futuro cuando un tercero conserva el ciphertext y eventualmente obtiene la clave.

STORAGE.md establece dos copias para documentos públicos estables, comprobaciones periódicas de recuperación y presupuesto de conservación. La duración de un pin comercial depende de la cuenta y las condiciones contratadas. Eliminar un pin reduce nuestra participación en la conservación; no envía una orden de borrado a nodos ajenos ni retira capturas, cachés o copias descargadas.

resultados

Resultados e interpretación

La página calcula SHA-256 del documento y un CIDv1 raw válido para esos bytes. Además recupera venture-hello.json desde el mismo Live Server y compara su contenido binario con el objeto declarado. Esa recuperación es local y verificable; no se presenta como descarga desde Pinata. Al elegir versión 2 cambia un byte relevante del JSON y obtenemos un hash y un CID diferentes.

El resultado prueba la relación entre bytes e identidad dentro del codec elegido. No prueba que un proveedor haya almacenado el objeto. La respuesta HTTP ilustrativa muestra la estructura esperada de un gateway, mientras que el control de pin explica por qué una copia administrada ayuda a la disponibilidad. Mantener ese límite permite interpretar correctamente tanto una comprobación exitosa como una falla de transporte.

analisis

Análisis crítico

Publicación y eliminación

El contenido público puede ser descubierto, copiado y redistribuido. Eliminar nuestro archivo local y cancelar un servicio no recupera las copias de terceros. El riesgo aumenta cuando un dato adquiere significado más tarde: un alias inocuo puede vincularse con una persona mediante otra base. Por ello excluimos datos personales incluso cuando el ejercicio solo necesita una demostración pequeña.

Dependencia operacional

Un gateway mejora usabilidad pero incorpora observación de solicitudes, políticas de acceso y límites propios. La aplicación puede prever gateways alternativos y verificar contenido, aunque eso requiere diseño explícito. También conviene reconocer que el pinning puede concentrarse en pocos proveedores: una arquitectura distribuida puede tener una operación frágil si depende de una sola cuenta. Nuestro diseño combina clasificación previa, copias y comprobaciones de recuperación en lugar de asumir disponibilidad por la existencia de un CID.

conclusiones

Conclusiones

  1. La identidad por contenido depende de bytes y representación. El experimento con dos versiones demuestra por qué un cambio mínimo modifica el CID y por qué los parámetros de importación deben documentarse.
  2. El CID identifica, mientras que el pinning conserva. Separar ambas funciones evita interpretar un identificador válido como garantía de una descarga disponible o de permanencia ilimitada.
  3. Una recuperación necesita comprobar transporte e integridad. La comparación local reproduce la segunda comprobación sin atribuir al gateway una operación que no se realizó.
  4. La política del venture determina qué puede publicarse. Seleccionar contenidos estables y no sensibles reduce riesgos que ninguna promesa de eliminación distribuida puede resolver.
